## Задание 1. СУБД

### 1.1. Бюджетирование, финаналитика и прогноз рисков

**Что бы я взял:** реляционную СУБД — **PostgreSQL** (или Oracle / MS SQL,
если компания уже на них).

**Почему:**

- Финансы — это то место, где данные **нельзя терять и путать**.
  ACID-транзакции и ограничения (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK`,
  `NOT NULL`) — ровно то, что нужно.
- Схема описана заранее: проекты, статьи бюджета, план/факт, периоды.
  Это удобно для финансов.
- Аналитику и прогнозы можно считать прямо в SQL — агрегаты, оконные
  функции, CTE. Сверху накрутить BI (Metabase, Power BI).
- Для ML/прогноза рисков есть `MADlib` или `PL/Python` прямо в Postgres,
  либо выгрузка в Python/R.

**Что бы я сделал как DevOps:**

- Поднял бы **реплику для чтения**, чтобы аналитика не грузила
  операционную базу.
- Настроил бы **бэкапы** (pg_dump + WAL-архивация) и **point-in-time
  recovery**.
- Для тяжёлой аналитики, если данных станет много, вынес бы отчётность
  в **ClickHouse** — но это уже на будущее.

#### 1.1.* Ускорение хеширования

Сначала бы разобрался, **что именно тормозит**: сам алгоритм хеширования
в приложении или хеш-индексы внутри СУБД.

**Если это в приложении:**

- Проверить алгоритм. Если `MD5`/`SHA-1` — менять. Для паролей —
  `bcrypt`/`Argon2`, для контрольных сумм — `BLAKE3` или `SHA-256`.
- Использовать **OpenSSL EVP API** (`EVP_DigestInit/Update/Final`) —
  он автоматически подхватывает аппаратное ускорение (AES-NI,
  Intel SHA-NI).
- **libsodium** — удобная обёртка над современными алгоритмами
  (`crypto_generichash`, `crypto_pwhash`).
- Для массовых вычислений — **GPU**: CUDA/OpenCL + Hashcat.
- Кэшировать уже посчитанные хеши в **Redis**, если данные повторяются.
- Считать хеши **батчами**, а не по одному.

**Если это хеш-индексы в Postgres:**

- Поднять `work_mem`, `shared_buffers`, `maintenance_work_mem`.
- Строить индексы в непиковые часы (`CREATE INDEX CONCURRENTLY`).

### 1.2. Лендинги + CRM

**Лендинги:** тут данные **разнородные** — UTM-метки, формы разной
структуры, события, клики. Жёсткая схема мешает. Я бы взял:

- **MongoDB** — гибкая схема, быстрая запись, шардирование.
- **Redis** — для горячего: счётчики, сессии, rate limiting, очередь
  лидов.

**CRM:** зависит от зрелости.

- Если это сделки, клиенты, воронки, задачи, платежи со связями →
  **PostgreSQL** (JOIN'ы, отчёты, ACID).
- Если CRM стартапная и поля часто меняются → **MongoDB**.

Как DevOps: поднял бы **docker-compose** с Mongo + Redis + Postgres,
настроил бы **бэкапы** и **мониторинг** (Prometheus + Grafana).
Для лендингов — отдельный инстанс Mongo, чтобы нагрузка не била по CRM.

#### 1.2.* Можно ли закрыть одной СУБД?

**Да, и я бы выбрал PostgreSQL.**

Почему:

- **JSONB** позволяет хранить гибкие данные лидов с лендингов — по сути
  документная модель внутри реляционной.
- **GIN-индексы** по JSONB — быстрый поиск.
- Реляционное ядро закрывает CRM: клиенты, сделки, задачи, связи,
  отчёты.
- **pg_cron** + **LISTEN/NOTIFY** — фоновые задачи и уведомления.
- **PostGIS** — если понадобится гео (адреса объектов).

**Альтернатива:** MongoDB целиком — тоже реально, но отчёты и связи
в CRM будут сложнее.

**Гибрид:** PostgreSQL + Redis (Redis как кэш/очередь). Формально две
СУБД, но Redis — это скорее инфраструктурный слой, чем хранилище.

**Мой выбор:** PostgreSQL + JSONB. Одна СУБД, меньше зоопарка
в эксплуатации.

### 1.3. База корпоративных норм и обучающих материалов

**Что бы я взял:** MongoDB **или** PostgreSQL + JSONB.

Тут контент **иерархический**: разделы → подразделы → статьи →
вложения. Плюс версии, теги, автор, дата, привязка к подразделению.

- **MongoDB** — документ = статья, вложенные структуры, гибкие поля.
  Удобно для вики.
- **PostgreSQL + JSONB** — если хочется держать всё в одной СУБД.

Готовая альтернатива — **Confluence / Wiki.js / Outline**. Но если
«своя база», то Mongo или Postgres.

Как DevOps: поднял бы **Wiki.js** в Docker, подключил бы к Postgres,
настроил **SSO** через LDAP/Keycloak. Не изобретал бы велосипед.

#### 1.3.* Можно ли использовать уже существующую СУБД?

**Да, ту же PostgreSQL из 1.1/1.2.**

Как реализовал бы:

- Отдельная **схема** `knowledge_base` или отдельная БД `kb`.
- Таблицы: `sections`, `articles`, `article_versions`, `attachments`,
  `tags`, `article_tags`, `departments`.
- Контент — `TEXT` или `JSONB`.
- **Полнотекстовый поиск** — `tsvector` + GIN-индекс (русский словарь
  настраивается).
- Версионирование — `article_versions` с `valid_from`/`valid_to`.
- Доступ — роли Postgres + **RLS** (Row-Level Security) по
  подразделениям.

Как DevOps: настроил бы **отдельную роль** для приложения
с ограниченными правами, **бэкап** этой схемы отдельно, **мониторинг**
размера таблиц.

### 1.4. Логистика: маршруты и распределение курьеров

**Что бы я взял:** **Neo4j** (графовая) + **PostgreSQL** для
операционных данных.

Задача — **быстрая работа со связями**:

- Объекты, склады, поставщики, курьеры, дороги — **узлы**.
- Расстояния, время, ограничения, загрузка — **рёбра** с весами.

Графовая СУБД даёт:

- Быстрый поиск кратчайшего пути (Дейкстра, A*).
- Оптимизацию маршрута (TSP, VRP).
- Гибкость при изменении топологии.

**Альтернатива:** PostgreSQL + **pgRouting** (расширение PostGIS). Если
не хочется отдельную СУБД — рабочий вариант.

**Дополнительно:** Redis для кэша маршрутов и позиций курьеров,
**OR-Tools** для тяжёлой оптимизации.

Как DevOps: Neo4j в Docker, **бэкапы** дампом, **мониторинг** через
Prometheus exporter. Связка с Postgres — через **Kafka** или ETL
(Airbyte).

#### 1.4.* Подключать ли отдел закупок?

Два пути:

**Вариант A — подключить закупки к Neo4j.**

- Плюс: единая картина связей «поставщик → материал → склад → объект».
- Минус: закупки — это транзакционные документы, а не граф. Хранить их
  в графе неудобно.

**Вариант B — своя СУБД для закупок + связка с логистами.**

- Закупки — **PostgreSQL** (документы, суммы, статусы, ACID).
- Логистика — **Neo4j** (маршруты, связи).
- Связка через **ETL/CDC** (Debezium, Airbyte) или общий ID.

**Моя рекомендация:** вариант B. Каждая СУБД делает то, что умеет
лучше. Синхронизация — через **Kafka** или материализованные
представления.

Как DevOps: поднял бы **Debezium** для CDC, **Kafka** для шины,
настроил бы **мониторинг лага** репликации.

### 1.5.* Можно ли всё решить одной СУБД?

**Да, но с оговорками.** Универсальный кандидат — **PostgreSQL**.

Почему:

- Реляционное ядро — бюджеты, финансы, закупки, CRM, корпоративные
  нормы.
- **JSONB** — гибкие данные лендингов, лиды, контент базы знаний.
- **PostGIS + pgRouting** — гео и маршруты.
- **Полнотекстовый поиск** — база знаний.
- Расширения: `pg_cron`, `MADlib`, `TimescaleDB`, `Citus`.
- Реплики и партиционирование — масштабирование.

Ограничения:

- Графовые запросы (рекурсивные CTE) медленнее, чем в Neo4j, на
  глубоких обходах.
- Для миллиардов строк аналитики Postgres проигрывает **ClickHouse**.
- На практике всё равно появляется **polyglot persistence** — несколько
  СУБД под разные задачи.

**Вывод:** PostgreSQL — лучший «единый» выбор, но графовую логистику
и тяжёлую аналитику лучше выносить отдельно.

Как DevOps: если всё в одном Postgres — настроил бы **Citus** для
шардирования заранее, чтобы потом не переезжать.

## Задание 2. Транзакции

### 2.1. Пополнение баланса телефона — 6 шагов

1. **Инициализация.** Пользователь вводит номер и сумму, платёжная
   система создаёт транзакцию со статусом `PENDING` и уникальным
   `transaction_id`.
2. **Проверка.** Валидация номера, суммы, лимитов, проверка, что
   счёт/карта активны и достаточно средств.
3. **Резервирование.** На стороне банка/шлюза средства **блокируются**
   (authorization hold), но ещё не списываются.
4. **Списание и зачисление.** Банк списывает деньги, оператор связи
   зачисляет их на баланс абонента. Оба действия — в рамках одной
   логической транзакции (или через компенсацию, если системы разные).
5. **Фиксация (commit).** Транзакция переводится в статус `SUCCESS`,
   изменения записываются в БД оператора и платёжной системы.
6. **Подтверждение и уведомление.** SMS/push, чек, обновление баланса
   в личном кабинете. Запись в журнал аудита.

Если на любом шаге сбой — **rollback**: блокировка снимается, статус
`FAILED`, деньги возвращаются.

Как DevOps: настроил бы **идемпотентность** по `transaction_id`,
**ретраи** с экспоненциальной задержкой, **алерты** на количество
`FAILED` транзакций.

#### 2.1.* Пополнение через автоплатёж

Отличия:

1. **Триггер.** Не пользователь, а **планировщик** (cron/шедулер) или
   событие «баланс ниже порога».
2. **Сохранённый способ оплаты.** **Токенизированная карта**
   (PCI DSS token) — без ввода данных.
3. **Авторизация.** Шлюз проводит списание по токену (с 3-D Secure или
   без — зависит от настроек).
4. **Списание и зачисление.** Аналогично ручному: банк → оператор →
   баланс.
5. **Фиксация и логирование.** Транзакция `SUCCESS`, запись в историю
   автоплатежей.
6. **Уведомление.** SMS/push. Если не удалось — уведомление об ошибке
   и **retry** по расписанию.

Дополнительно: настройки автоплатежа (порог, сумма, период),
возможность отключения, лимиты, **idempotency key** против двойного
списания.

Как DevOps: вынес бы шедулер в отдельный сервис (K8s CronJob),
настроил **мониторинг** успешности автоплатежей.

## Задание 3. SQL vs NoSQL

### 3.1. Пять преимуществ SQL-систем

1. **ACID-транзакции.** Атомарность, согласованность, изоляция,
   durability. Критично для финансов, заказов, бронирований.
2. **Строгая схема и целостность.** Ограничения, внешние ключи, типы
   данных — меньше мусора и аномалий.
3. **Мощный язык запросов (SQL).** JOIN'ы, агрегаты, оконные функции,
   подзапросы, CTE. Один язык — для всего.
4. **Зрелость и стандартизация.** Огромная экосистема, инструменты,
   документация, специалисты. SQL знают все.
5. **Надёжность и предсказуемость.** Проверенные десятилетиями СУБД,
   репликация, бэкапы, PITR.

Бонусом: **гибкость отчётности** — аналитики и BI любят SQL.

Как DevOps: SQL-системы проще **бэкапить**, **реплицировать**
и **мониторить** — куча готовых инструментов (pgBackRest, Percona
Toolkit, pg_exporter).

### 3.1.* Преимущества NewSQL

**NewSQL** (CockroachDB, Google Spanner, TiDB, YugabyteDB, VoltDB) —
попытка взять лучшее от обоих миров.

**Перед классическим SQL:**

- **Горизонтальное масштабирование** без ручного шардирования.
- **Геораспределённость** — данные рядом с пользователем, низкая
  latency.
- **Отказоустойчивость** на уровне нескольких дата-центров
  «из коробки».
- **Высокая пропускная способность** на запись.

**Перед NoSQL:**

- **ACID + SQL** — не нужно жертвовать согласованностью ради масштаба.
- **Строгая схема** (или гибкая, но контролируемая).
- **Знакомый инструментарий** — BI, ORM, драйверы работают как
  с обычным SQL.
- **Меньше «зоопарка»** — не нужно строить согласованность вручную
  поверх eventual consistency.

**Минусы:** сложнее в эксплуатации, меньше специалистов, цена. Если
данных немного — обычный PostgreSQL проще и дешевле.

Как DevOps: NewSQL — это **StatefulSet в K8s** с кучей нюансов.
Пока не готов рекомендовать без опыта.

## Задание 4. Кластеры

**Условие:** огромный объём данных, 1000 машин, много вычислений.

### Критерий выбора типа СУБД

Главное — **характер нагрузки**:

1. **Тип нагрузки:** OLTP или OLAP? При 1000 машинах и «много
   вычислений» — почти наверняка **OLAP / batch**.
2. **Модель согласованности:** строгий ACID или eventual consistency?
3. **Модель распределения данных:** шардирование, репликация,
   партиционирование.
4. **Модель вычислений:** MapReduce, DAG, streaming, in-memory.
5. **Latency:** секунды, минуты, часы?
6. **Стоимость и сложность эксплуатации.**

### Какая модель распределённых вычислений лучше

**Ответ: DAG-модель (Apache Spark) — предпочтительнее, чем
классический MapReduce.**

Почему:

- **MapReduce (Hadoop)** — классика для батч-обработки.
  Отказоустойчивость через HDFS, data locality. Но много дискового
  I/O, медленно для итеративных задач.
- **Apache Spark (DAG + in-memory)** — быстрее MapReduce в 10–100 раз
  на итеративных алгоритмах (ML, графы). Поддерживает SQL, streaming,
  MLlib, GraphX. Отлично ложится на 1000 машин через
  **YARN/Kubernetes**.
- **Flink** — если нужен streaming.
- **ClickHouse** — если нужны быстрые SQL-запросы по большим данным.
- **Хранение:** HDFS или S3/MinIO + **Parquet/ORC** (колоночное
  сжатие).

### Итоговая рекомендация

**Платформа:** Apache Spark + HDFS/S3 + Parquet — для batch и ML.

**Модель:** DAG в Spark/Flink — оптимизация плана, in-memory шаффлы,
отказоустойчивость через lineage (RDD).

**Критерий в одну строку:** аналитика и batch → Spark на DAG;
интерактивные SQL → ClickHouse; streaming → Flink.

Как DevOps: поднял бы **Kubernetes** + **Spark Operator**,
**S3/MinIO** для хранения, **Prometheus + Grafana** для мониторинга,
**Airflow** для оркестрации. 1000 машин — это уже серьёзный кластер,
нужен **autoscaling** и **cost control**.
